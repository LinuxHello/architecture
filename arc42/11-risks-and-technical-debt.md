# 11. Risks and technical debt

Part of the [Arc42 architecture documentation](README.md).

This section answers the question: what could still go wrong with the design, and which shortcuts were taken on purpose? It has three lists. **Open questions** are things not decided yet, some of which block a part of Linux Hello. **Risks** are things that could hurt users or the project even with the present design, each with a rating and what is done about it. **Technical debt** is a shortcut taken knowingly, with what paying it back would mean. A newcomer who wants to help will find the most important unsolved problems here. Terms that may be new to you are in the [glossary](12-glossary.md).

Questions are answered by *spikes*, short experiments recorded in [spikes/](../spikes/README.md); code that depends on an open question waits for its answer.

## 11.1 Open questions

**How is a fingerprint or face match tied to the TPM?** The PIN unlocks the user's keys in the TPM, because the TPM itself checks it. A fingerprint or face match, by contrast, is a yes or no that fprintd or Howdy reports to the Agent; the TPM cannot check it. If the Agent simply believed the yes, unlocking the keys would come down to a flag in the Agent's memory, which is exactly what the design wants to avoid (invariant 1 of [linux-hello's AGENTS.md](https://github.com/LinuxHello/linux-hello/blob/main/AGENTS.md#invariants)). An ADR and a spike are to compare the options. This question blocks the TPM provider, and the decision is hard to undo ([linux-hello#136](https://github.com/LinuxHello/linux-hello/issues/136)).

**Which accounts must keep their passkeys in the TPM?** The policy can hold a website to the TPM, but there is no rule yet for deciding which websites deserve that, such as banks, work accounts or the email account that resets every other password. It needs a rule for classifying accounts by how much harm their loss would do.

**How long do desktop apps' logins last, and where are their tokens kept?** The problem behind [section 4.4](04-solution-strategy.md#44-signing-in-again-without-the-user) was seen with Claude Desktop, whose login expires within a day. That was observed on one machine, not measured, and whether such apps store their tokens in KWallet or through libsecret was not checked.

Two questions were answered by spikes on 2026-11-17 and now wait for a decision record and code:

- **How can one virtual security key belong to only one user?** If two people are signed in on the same computer, both could see the virtual security key. [Spike 0138](../spikes/0138-virtual-ctap-session-binding.md) showed a way: a udev rule gives the device to one user, and the Agent creates it only while that user's session is in front and unlocked, and removes it within a fraction of a second when the session locks or switches. An ADR should record it ([linux-hello#138](https://github.com/LinuxHello/linux-hello/issues/138)).
- **How does the Agent know that the confirmation window is its own?** The Prompt UI, the window that asks the user to confirm a passkey, runs in the user's session, where any other program of the same user could imitate it. [Spike 0177](../spikes/0177-prompt-identity-in-the-users-session.md) found that no check on a connection from the user's session can tell the real window from a copy. Its answer is that the window must never decide on its own: proof that the user is there comes from the fingerprint sensor or from the PIN, which the Agent checks itself. A [follow-up spike](../spikes/0177-prompt-launch-by-the-system-manager.md) showed that starting the window as a system service from the Agent removes one way of faking it. The confined window itself is [linux-hello#175](https://github.com/LinuxHello/linux-hello/issues/175); the spike is [linux-hello#177](https://github.com/LinuxHello/linux-hello/issues/177).

## 11.2 Risks

The ratings come from two places. Risks recorded as issues in the code repository carry the severity given in the issue. Risks found by spikes are rated in words from the evidence in the spike. "Not rated" means the risk is known and accepted but nobody has weighed it yet. The list is not complete: the threats in [section 8](08-crosscutting-concepts.md#threats-to-design-against) and the consequences in [section 4](04-solution-strategy.md#46-what-this-strategy-makes-easier-and-harder) are further inputs.

| Risk | Example or reason | Rating | What is done about it | Source |
| :-- | :-- | :-- | :-- | :-- |
| Another user on the same computer could use the virtual security key | Two people signed in with fast user switching; the key is visible to both, and nothing yet decides whose passkeys it serves or where the prompt appears | High | Spike 0138 found a design (one user per key, removed when the session locks or switches); an ADR and code are still to come | [linux-hello#138](https://github.com/LinuxHello/linux-hello/issues/138) |
| A biometric match is a yes or no from a program, which the TPM cannot check | See the first open question above | Blocks the TPM provider | An ADR and a spike are to compare the options | [linux-hello#136](https://github.com/LinuxHello/linux-hello/issues/136) |
| Any program of the user can change the user's own rules without the user proving who they are, and so lock the user out everywhere | A rogue program calls `SetUserPolicy` with a layer that allows no method at all | Medium | A verification before a policy change is planned. A user's layer can already never weaken an administrator's rule (the amendment of [ADR-0018](../adr/0018-user-policy-layer.md), still proposed) | [linux-hello#131](https://github.com/LinuxHello/linux-hello/issues/131) |
| A program of the user can draw a window that looks like the Prompt UI | The window then shows the wrong website name | Accepted | The window decides nothing: a fingerprint or the PIN, checked by the Agent, is the proof, so a fake window changes only what is shown, not what is signed ([ADR-0020](../adr/0020-presence-and-verification.md), spike 0177) | [linux-hello#177](https://github.com/LinuxHello/linux-hello/issues/177) |
| The helper that creates the virtual security key needs the right to create devices, and could misuse it | A compromised helper could create a fake keyboard and type into the session | Medium | It runs as its own user with its own AppArmor profile, without the TPM or the user's files; a udev rule stops its devices from acting as keyboards or mice ([spike 0121](../spikes/0121-uhid-helper-privilege.md)) | [ADR-0005](../adr/0005-provider-path.md) |
| Face recognition needs a root helper for setup, and runs Howdy's Python code when the user signs in | A flaw in Howdy's code runs with the rights of the helper; the policy rule `face_requires_ir` (only an infrared camera counts) cannot be checked | Medium | Specify and confine the helper, run the matcher without privileges in a sandbox, and enforce or drop `face_requires_ir` | [linux-hello#141](https://github.com/LinuxHello/linux-hello/issues/141), [spike 0008](../spikes/0008-howdy-interface.md) |
| After a PIN change, the old copy of the root key still opens with the old PIN | Someone who saved the old key file and knows the old PIN can still use the keys | Medium | Delete the old key file; consider a TPM counter that invalidates old copies; test again on a hardware TPM | [spike 0011](../spikes/0011-tpm-root-key-change-auth.md) |
| Howdy offers no camera picture, and its development branch may change how it answers | A new Howdy release could break the face check | Medium | Call Howdy as it is, with no live picture in 1.0; a test fixes how Linux Hello expects Howdy to answer ([ADR-0015](../adr/0015-face-capture-and-enrolment.md)) | [spike 0008](../spikes/0008-howdy-interface.md) |
| KDE's login and lock screens have no place for Linux Hello's prompt, and the lock screen differs between Plasma 6.6 and 6.8 | On Plasma 6.6 the lock screen has no separate face service | Medium | A shared prompt component, a login screen theme of Linux Hello's own, and KDE's own services at the lock screen, text only ([ADR-0016](../adr/0016-prompt-hosts.md)) | [spike 0009](../spikes/0009-plasma-prompt-component.md) |
| The name "Linux Hello" shares the word "Hello" with Microsoft's registered trade mark WINDOWS HELLO for the same kind of software | Microsoft could object to the name | Moderate; not legal advice | A trade mark attorney reviews the name before the first release; fallback names are Lychgate and Thresholdkey. A rename would cost the D-Bus names and crate names | [spike 0014](../spikes/0014-name-trademark-risk.md) |
| A new account that gets the user number of a deleted account inherits its rules, and later its keys | An administrator deletes user 1001 and creates a new user, who gets 1001 again | Low | Record who each state directory belongs to and set it aside on a mismatch; remove the state of deleted users | [linux-hello#143](https://github.com/LinuxHello/linux-hello/issues/143) |
| Browsers treat Linux Hello as a security key, not as part of the computer | A website cannot tell it apart from a USB key; the browser cannot route by website | Low: it works end to end with stock browsers ([spike 0094](../spikes/0094-virtual-ctap-end-to-end.md), [spike 0120](../spikes/0120-resident-keys-presence-and-uv.md)) | Accepted for 1.0; the Agent routes by the website's name itself. Listed below as technical debt | [ADR-0005](../adr/0005-provider-path.md) |
| Face and PIN entries cannot appear on KDE's Users page | The user looks for them next to the fingerprint | Low | A settings page of Linux Hello's own next to Users | [spike 0010](../spikes/0010-kcm-users-extension-point.md) |
| The colour and infrared streams of a camera start unreliably together | Only one camera model was tested | Low in 1.0 | Howdy alone holds the infrared stream while it checks a face; test a second camera before any live picture is built | [spike 0012](../spikes/0012-camera-rgb-ir-concurrent.md) |
| Under X11 another program of the user can read a PIN typed into the prompt | X11, unlike Wayland, lets any program read the keys typed into another window | Not rated | Prefer the sensor; documented, not prevented; Wayland is tested before 1.0 | [ADR-0020](../adr/0020-presence-and-verification.md) |
| When Linux Hello is unavailable, the account password alone signs the user in, even where the policy asks for two factors | The Agent crashed at the login screen | Not rated | Accepted, so that a broken Linux Hello never locks anyone out; the password never unlocks the keys in the TPM | [ADR-0023](../adr/0023-pam-module-and-login-failure.md) |
| Only a software TPM, and only Ubuntu with AppArmor, have been tested | A hardware TPM may be slower or behave differently; Fedora uses SELinux instead of AppArmor | Not rated | Run the spikes again on a hardware TPM; decide which distributions are supported | [section 7](07-deployment-view.md) |

## 11.3 Technical debt

| Debt | Why it was taken on | What paying it back means |
| :-- | :-- | :-- |
| Browsers show Linux Hello as a security key, not as "this device" | A virtual security key works with every browser today, without a change in any other project ([ADR-0005](../adr/0005-provider-path.md)) | Offer Linux Hello as part of the computer (a *platform authenticator*) once the Linux desktop has a way to do so |
| Part of the confinement checks still runs by hand from the maintainer's private repository | They were first written for a test virtual machine | Run all of them in CI ([linux-hello#149](https://github.com/LinuxHello/linux-hello/issues/149); the first part runs there since [linux-hello#239](https://github.com/LinuxHello/linux-hello/pull/239)) |
| The policy engine reads and parses every policy file for each decision | Simple and correct first | Keep the effective policy in memory and reload it when a file changes ([linux-hello#151](https://github.com/LinuxHello/linux-hello/issues/151)) |
| The amendment of [ADR-0018](../adr/0018-user-policy-layer.md) of 2026-11-10 is still proposed, but the code already follows it | The code needed the rule before the decision was formally taken | Accept the amendment, or change the code |

## Questions answered earlier

Two early questions shaped the strategy and are settled. credentialsd, a proposed Linux passkey service, offered no way for Linux Hello to plug in its own key store ([spike 0005](../spikes/0005-credentialsd-provider-api.md)), and neither Firefox nor Chromium calls the Linux credentials portal ([spike 0006](../spikes/0006-browser-webauthn-portal.md)). So Linux Hello appears to browsers as a USB security key instead ([ADR-0005](../adr/0005-provider-path.md)), which a prototype showed working end to end ([spike 0094](../spikes/0094-virtual-ctap-end-to-end.md)). The questions about Howdy, KDE's prompts and the Users page were answered by spikes 0008, 0009 and 0010; what remains of them is in the risks above.
